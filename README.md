# msgbroker

Go replacement for JobScheduler. **周期消息** retain the existing frontend, URL routes and MySQL job/history tables. **定时消息** add Topic-based, one-time HTTP delivery with producer idempotency, retry and recovery. No SDK and no ordered queues in this release.

## Run

Go 1.25, MySQL 8 (InnoDB), and the existing environment variables:

```sh
export DATABASE_URL='mysql+pymysql://user:password@localhost:3306/job_scheduler'
export AGENT_API_TOKEN='your-existing-token'
go run ./cmd/msgbroker
```

The service listens on `:8000`; templates and assets are embedded. `GET /healthz` checks the database. `DISPATCH_ENABLED=false` disables all background dispatch and health jobs for review; explicit manual/API mutations still work. Do not point a review instance at a production database: startup performs additive migrations.

One dispatcher checks due work every second. `DELIVERY_WORKERS` configures concurrent HTTP deliveries (positive integer, default `1024`); changing it requires a restart. Delivery workers do not poll the database, and the dispatcher only claims messages for available workers, so waiting messages remain persisted without starting their delivery lease early.

The old `/`, `/jobs/*`, `/static/*`, and `/openplatform/v1/jobs/*` routes remain. Templates, styles and the UUID-at-cursor behavior are retained from JobScheduler; navigation adds 定时消息 and Topic 配置. The new API is documented in [docs/api.md](docs/api.md).

## Model

```text
legacy jobs / cron ── generate next occurrence ──┐
                                               ├─ messages + message_waits ── HTTP callback
external HTTP API ── topic + uniqueId + runAt ───┘
```

A periodic occurrence rolls its next message forward when it becomes ready, in the same transaction, not when its callback finishes. Original cron jobs retain HEAD preflight, max-one-in-flight per job, the 30-second misfire grace and single-attempt behavior. A stopped process resumes persisted plans and skips obsolete cron occurrences, without replaying every missed interval. Timed messages move from pending to delivering (including retry waits) to completed with a success/failed/cancelled result; late messages are not discarded.

`(topic_id, unique_id)` guarantees creation idempotency: duplicate submissions return the original message without comparing or replacing its payload/time. Defaults are 16 total attempts with uncapped exponential waits starting at 5 seconds. Failed messages are retained in the failure queue for manual redelivery. HTTP delivery is at-least-once within the configured retry budget. Consumers own business idempotency using their payload. A 2xx acknowledges receipt, not completion of asynchronous business work. Topics may share a URL, but the body is always the payload with no wrapper or required message-ID header.

## Compatibility and rollout

Read [docs/compatibility.md](docs/compatibility.md) before replacing an instance. Existing tables and IDs are retained; additional columns hold dispatch progress and health-probe sequencing. Do not run the Python scheduler and Go dispatcher against the same active jobs simultaneously. No production switching is automated by this repository.

## Verification

```sh
go test ./...                       # unit tests; SQL tests explicitly skip without DSN
TEST_MYSQL_DSN='root:password@tcp(127.0.0.1:3306)/' go test -race -count=1 ./...
go vet ./...
node --test tests/test_uuid_insertion.cjs
```

Integration tests create randomly named `msgbroker_test_*` databases and drop only those databases. Use a dedicated test server with CREATE/DROP DATABASE permission. A GitHub Actions template in `docs/ci/github-actions.yml` runs the same tests against MySQL 8 plus a Docker build. It is not activated: the current GitHub credential lacks the `workflow` scope. `testdata/apscheduler.json` contains trigger times generated by APScheduler 3 for legacy cron compatibility.
